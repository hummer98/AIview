Design Review 001 — 前回の表示位置を復元

Reviewer: design-reviewer (independent)  ·  Reviewed: plan 001 / ADR 001  ·  Date: 2026-06-06

判定: 修正してから GO。 ADR の後方互換設計は健全。だが計画の中核前提「記録は jumpToIndex にのみ置けば初期表示の上書きを防げる」が、 フィルタ／サブディレクトリ操作が すべて jumpToIndex を経由する現実装と噛み合っておらず、 意図しない記録と AC5/AC6 のテスト不能を生む。下記 B1–B3 を解消すれば実装に渡してよい。

Blockers

B1. 「記録は jumpToIndex のみ」前提が、フィルタ／サブディレクトリの自動ジャンプを巻き込む

なぜ問題か: 計画は「初期表示は jumpToIndex を経由しないので記録されない／移動だけが記録される」を安全性の根拠にしている。 しかし現実装では以下がすべて jumpToIndex を経由する:

  • setFilterLevel（行810-814）: フィルタON時に現在画像が対象外なら先頭該当へ jumpToIndex。
  • handleFilteredIndexChange（行848-864）: お気に入り変更でフィルタから外れた時に jumpToIndex。
  • syncCurrentIndexByAnchor（行1414-1435）: currentIndex = -1 にしてから jumpToIndex。 setFilterLevelWithSubdirectories / disableSubdirectoryMode / clearFilterWithSubdirectories から呼ばれる。

計画は「非統合モード時のみ記録」で統合系を弾く想定だが、通常モードのフィルタON/OFF・お気に入り変更によるジャンプは非統合モードなので記録対象に入ってしまう。 結果、ユーザーが画像を「移動」していないのに lastViewedImage がフィルタ先頭などに書き換わる。 さらに setFilterLevel の自動ジャンプはフォルダオープン直後（プロンプト判定前後）にも起こりうるため、AC5 の「初期表示で記録しない」を破る経路になる。

推奨修正: 記録ゲートを「jumpToIndex を通ったか」ではなく「ユーザー主導のナビゲーションか」で定義する。具体的には

  • jumpToIndex(_ index:Int, recordLastViewed: Bool = false) のように明示フラグ化し、 moveToNext/Previous・カルーセル onSelect・スライドショー送り・confirmRestoreLastViewed のみ true を渡す。 フィルタ／サブディレクトリ／anchor 同期からの呼び出しは false（デフォルト）。
  • これで「経由するか」依存の暗黙ルールを廃し、AC5/AC6 を機械的に保証できる。

B2. 復元ジャンプ先が currentIndex==0 のとき jumpToIndex の同一indexガードで沈黙failする

なぜ問題か: jumpToIndex 冒頭に guard clampedIndex != currentIndex else { return } がある（行428）。 通常オープン直後の初期位置は currentIndex = 0。記録画像がたまたま index 0 に解決されるケースは AC6（記録==初期位置ならプロンプト出さない）で弾けるが、 プロンプトを出すのは「初期位置と異なる」場合に限るという条件と confirmRestoreLastViewed() が jumpToIndex(targetIndex) を呼ぶ実装が整合しているかは、targetIndex の確定タイミングに依存する。 特に handleScanComplete でソート後に index を再計算するため、プロンプト表示時の targetIndex と確定時の index がずれると、ガードに当たって移動が起きない（＝「移動」を押しても何も起きない）か、誤った位置へ飛ぶ。

推奨修正: lastViewedRestorePrompt に index を埋め込まずファイル名のみを保持し、 confirmRestoreLastViewed() 内で確定時点の imageURLs から index を再解決してから jumpToIndex(recordLastViewed: true) する。 index を AC4 のテストで検証する場合は、再解決後の currentIndex をアサートする形にする（プロンプト struct の targetIndex をテスト対象にしない）。

B3. AC5/AC6 が現状の公開APIでは単体検証できない（テスト可能性の欠落）

なぜ問題か: AC5「初期表示で記録しない」・AC6「統合モード除外」を確かめるには、 テストからディスク上の lastViewedImage を読む手段か、プロンプトが出る/出ないを観測する手段が要る。 現状 FavoritesStore には lastViewedImage の getter が無く、ImageBrowserViewModel にもプロンプト状態の公開プロパティが無い。 計画の実装ノートには lastViewedRestorePrompt 公開・getLastViewedImage() 相当が暗黙に含まれるが、AC として明文化されていないため inspector が「検証可能」と判定できない。 また既存 FavoritesE2ETests はすべて 0.8s デバウンスより長い 500ms 以上の sleep を多用しつつ即時アサートしており、記録フックを jumpToIndex に足すと、これらの既存テストの jumpToIndex 連打が意図せず lastViewedImage を書く副作用を持つ（テスト間でフォルダを使い回さないので破壊はしないが、AC2 の「favorites 保持」を確認する新テストが lastViewedImage 混入で誤検知しうる）。

推奨修正:

  • AC に観測点を明記する。例: 「FavoritesStore.loadFavoritesFromDisk(for:) 相当が FavoritesFile を返し、テストは .lastViewedImage を直接アサートする」。
  • プロンプト判定を副作用なく観測できるよう、viewModel.lastViewedRestorePrompt（nil/非nil）を AC3/AC6 の明示アサート対象として AC 本文に書く。
  • デバウンス記録は Task.sleep を含むため、テストは「sleep 後に書かれる」ことと「sleep 前は書かれない」ことの両方を検証する必要がある。AC1 にnegative 条件（移動直後・デバウンス満了前は未記録）を追記する。

Should-fix

S1. deleteCurrentImage がデバウンス記録と整合しない（記録が削除済みファイルを指す）

deleteCurrentImage（行465-493）は jumpToIndex を通らず loadCurrentImage を直接呼ぶ。B1 のフラグ方式なら記録はされないが、 削除直前に予約済みの 0.8s デバウンスTaskが、削除でずれた currentImageURL を後から記録する競合がある。 また「最後に表示していた画像」が削除済みファイル名のまま残ると、次回オープンで AC6 の「記録画像がフォルダ内に存在しない→プロンプト出さない」に落ちるので致命ではないが、 削除時に保留中の record Task を cancelしておくのが安全。推奨: deleteCurrentImage 冒頭で lastViewedRecordTask?.cancel()。

S2. record Task の対象フォルダと actor の currentFolderURL がずれる窓

FavoritesStore.setLastViewedImage(_:) は actor 内の currentFolderURL に書く設計（実装ノート）。 だが openFolder は冒頭で await favoritesStore.loadFavorites(for: url) を呼び currentFolderURL を即書き換える。 旧フォルダ向けに予約された 0.8s record Task が、新フォルダの loadFavorites 完了後に発火すると、旧フォルダのファイル名を新フォルダの favorites.json に書く。 計画は「openFolder 冒頭で record task cancel」と書いており方向は正しいが、cancel は await folderScanner.cancelCurrentScan() より前かつ loadFavorites より前に置くこと、 かつ setLastViewedImage 側でも記録時に対象フォルダURLを引数で渡して actor 内で currentFolderURL と一致確認する二重防御を推奨。フラグ＋cancel だけだと TOCTOU が残る。

S3. ADR の構造判別、optional 全欠落の legacy 空ファイル/空オブジェクトで誤判定の可能性

ADR は「legacy の値は Int なので FavoritesFile デコードは失敗し fallback する」と主張。これは概ね正しいが穴がある:

  • {}（空オブジェクト）: legacy の「お気に入り0件」も v2 の「favorites/lastViewed 両方nil」も {}。 FavoritesFile の両プロパティを optional にすると {} はv2デコード成功し favorites=nil→[:] になる。結果は無害だが、 「favorites を非optional [String:Int]」にすると {} はキー欠落でデコード失敗→legacy 経路。どちらでも結果 [:] なので実害なしだが、ADR が言う「favorites: [String:Int]（非optional）」前提なら {} は legacy 扱いになる点を明記すべき。
  • キー名 "favorites" を持つ実在画像: favorites.heic など。legacy {"favorites.heic": 3} は FavoritesFile デコードで favorites キー値が Int(3) → [String:Int] へのデコード失敗 → legacy fallback。ADR の主張どおり安全。ただし {"favorites": 3}（拡張子なし）という病的ケースも同じく Int なので安全。問題なし。

推奨: favorites を非optional（var favorites: [String:Int] = [:]）にし、判別ロジックを「v2 decode 成功 かつ favorites キーが存在」ではなく単純な try/catch fallback に保つ。 AC2 のテストに空オブジェクト {} と {"favorites": 1} の2病的ケースを追加するよう T4 に明記。

S4. 設定トグルが「記録ではなくダイアログのみ」を制御する判断の副作用

計画自身が「承認時に確認」とフラグ済み。レビューとしての所見: トグルOFFでも記録し続ける設計は、OFFにしたユーザーが「もう .aiview に状態を書いてほしくない」意図だった場合に裏切る。 CLAUDE.md は「ユーザーフォルダに .aiview が残るのは許容」としているので致命ではないが、 プライバシー観点（このアプリは privacy mode を持つ＝痕跡を気にするユーザー層がいる）ではOFF=記録も停止のほうが直感的。 推奨: 最低限、トグルの説明文に「OFFでも前回位置は記録されます（確認のみ無効）」と明記。あるいは OFF で記録も止める案を採用（実装コストはフラグ1つで差は小さい）。lead がユーザーに最終確認すべき。

Nice-to-have

N1. スキャン完了後プロンプトの UX 順序

巨大フォルダで「先頭画像を表示→数秒後にプロンプト」が出ると、ユーザーが先頭を見始めた後で割り込まれる。計画も risk として認識済み。 推奨: handleFirstImage でなく handleScanComplete 完了直後に最小遅延で出す現設計でよいが、 プロンプト表示中にユーザーが矢印キーで移動したらプロンプトを自動 dismiss（＝ユーザーは既に意思表示した）するガードを入れると角が取れる。

N2. ファイルパス指定オープン（openFile）+ 記録ありの二重意図

AC3 は「明示ファイル指定でも記録があればプロンプト表示」。だが openFile はユーザーが特定画像を名指しで開いた意図が強い。 そこに「前回の別画像へ移動しますか？」が出るのは人によっては煩わしい。仕様決定済み（ユーザー確認済み）なので尊重するが、 pendingInitialImageURL が記録画像と異なるときだけ出す（同一なら無音）ことは AC6 で既にカバーされている。実装時に pendingInitialImageURL 経路の index 確定（行546-550）と prompt 判定の順序を handleScanComplete 内で正しく直列化すること。

N3. ファイル所有権マップは衝突なし

T1=Data, T2=Domain, T3=Presentation, T4=Tests で重複なし。逐次実装方針も妥当。ただし B3 で FavoritesStore に観測用 API を足すため、 T1 と T4 の境界（テストが触る公開API）を T1 着手時に確定させること。FavoritesE2ETests.createFavoritesFile は legacy 形式を書くので、AC2 の移行テストの土台として再利用可。
