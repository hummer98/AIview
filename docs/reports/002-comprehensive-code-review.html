3. P0 — 次リリース前に直すべき所見

STATE-01 / P0

表示画像と currentImageURL が別物になり、削除対象を誤る

事実: 最初に列挙された画像を表示した後、scan完了時に配列をソートしてから currentImageURL を読み直している。したがって「実際にload済みのURL」ではなく「新しい配列の同じindex」をanchorとして採用する。DirectoryEnumeratorの順序はソート順とは限らない。サブディレクトリ有効化でも配列だけを差し替え、画像・indexを同期していない。

ImageBrowserViewModel.swift 655–696, 1458–1491。削除は587–617で currentImageURL を対象にするため、画面で見ている画像と違うファイルをTrashへ送る可能性がある。

修正: 選択状態を Selection(url, index, image) の1値としてcommitし、loadedImageURL == imageURLs[currentIndex] を常時不変条件にする。配列差替え前に loadedImageURL をcaptureし、新配列でindexを解決、存在しなければ先頭をreloadする。削除直前にも表示URL一致をguardする。

必須テスト: 列挙順と名前順が異なる3画像、subdirectory追加で先頭が変わるケース、表示画像と削除URLの一致。

MEM-01 / P0

LRUキャッシュの双方向ノードが循環参照し、clear後も画像を解放しない

事実: CacheNode.prev と next が双方strongである。通常evictionはlinksを切るが、clearMemoryCache() は辞書とhead/tailだけを捨て、各node間のlinksを切らない。2node以上あれば相互保持が残り、各nodeが大きなNSImageを保持し続ける。同じ実装がfull-sizeとthumbnailの2系統にある。

CacheManager.swift 11–17, 152–160 / ThumbnailCacheManager.swift 10–15, 234–243。

修正: 通常は weak var prev とし、clear時も防御的に全nodeのlinksを切る。LRUの所有権を値型のkey列へ寄せる選択肢もある。NSImage.representations.firstだけのサイズ推定も、実際のCGImageのbytesPerRow × height等へ改める。

検証: deinit probe/weak sentinelを用いた単体テストに加え、Instruments Leaks + Allocationsでclear前後のpersistent bytesを測る。既存テストはcountが0になることしか見ず、解放は検証していない。

ASYNC-01 / P0

フォルダ切替のキャンセルが実質機能せず、古いscanが新しい状態を上書きする

事実: FolderScanner.currentScanTask は宣言されるが一度も代入されない。共有boolean isCancelled は新scan開始時にfalseへ戻される。actorはcallbackのawaitで再入可能なので、Aをscan中にBを開くと、Aをcancel→Bがfalseへreset→Aが続行できる。ViewModelのcallbackにもfolder URLやgenerationの照合がない。

FolderScanner.swift 38–55, 90–128, 131–135 / ImageBrowserViewModel.swift 265–339。

影響: Aのfirst/progress/complete/errorが、すでにBを表示中の imageURLs、favorites、loading/error、warmerを上書きする。

修正: FolderSessionID（UUID）をopen開始ごとに発行し、await後と全commit直前に一致をguardする。Scannerはcallback3本ではなく AsyncThrowingStream<ScanEvent> または結果値を返し、所有するTask handleを確実にcancelする。CancellationErrorはUI errorにしない。

SCENE-01 / P0

scene固有状態をアプリ全体の AppState に置き、全windowへbroadcastしている

事実: AIviewAppが1個の@State AppStateを全WindowGroupへ注入する一方、各windowは個別ViewModelを持つ。folder picker、recent folder、reload、cache clear、sibling navigation、zoomは共有slot/booleanを各windowが監視して消費する。hasCurrentFolder / hasImagesとmetrics collectorも最後に更新したwindowが勝つ。

AIviewApp.swift 19, 32–58 / AppState.swift 19–125 / MainWindowView.swift 8–74。

現在

AppState 1個

↓ picker / zoom / reload / metrics

Window A・B・Cが同じイベントを監視・clear

→

推奨

App-global: settings / telemetry / shared services

Scene: BrowserSession / commands / metrics

メニューはfocused sceneへ配送

修正: windowごとにBrowserSessionを生成し、transient commandとavailabilityはそこへ置く。メニュー配送はFocusedValues / focused scene actionを使用する。アプリ全体へ残すのは設定、テレメトリ、共有cache service等だけにする。

SEC-01 / P0

稼働中のmetrics Workerが第三者の書込みとURL credential露出を許す

事実: GET /pingはIDが空でないことと長さしか検証せず、認証・署名・rate limitがない。CORSは*で、任意のbrowser/botからD1を汚染できる。stable install UUIDをqueryへ置くため、URLログや中間系へ残りうる。/stats?key=...も秘密をquery stringへ置く。

cloudflare/aiview-metrics/src/index.ts 22–75, 88–90 / TelemetryService.swift 41–74。

修正: pingはPOST JSON + Cache-Control: no-store、UUID形式・field allowlistを検証し、Cloudflare Workers Rate Limiting bindingを追加する。濫用耐性が必要ならinstallごとのserver-issued tokenまたは署名を導入する。statsはAuthorization: Bearer header + timing-safe compareへ移し、全応答をno-storeにする。D1はversioned migrationへ移す。

4. P1 / P2 — 構造・運用品質の所見

ASYNC-02 / P1

Taskの所有権とcleanupが不安定

  • 古いthumbnail warmerが完了時にthumbnailWarmingTask = nilとし、新しいTaskのhandleを消せる（VM 765–781）。
  • ThumbnailActivityModelとSlideshowTimerはself所有の無限Task内で、sleepを跨いでselfをstrong保持する。明示stopされないscene closeで循環が残りうる。
  • ImageLoader.prefetchTasksは完了時に削除されず、再prefetchを阻害する。loading cleanupもURLだけでremoveするので、新しい同URL Taskを遅いwaiterが消せる。
  • Toastは「既存タイマーをキャンセル」とコメントするがhandleを保持せず、古いtimerが新toastをdismissできる。

対策: Task token/identityと所有者を明示し、cleanupは「自分が現行なら」のみ行う。sceneのonDisappear/deinitでstop。可能な箇所はstructured concurrencyへ。

STATE-02 / P1

情報パネルのmetadataが画像遷移に追従しない

metadata loadはpanelを開いた瞬間に1回だけuntracked Taskで起動され、navigationでは再実行されない。完了時にもrequested URLと現在URLを照合しないため、遅いAの結果がB表示中にcommitされる。

ImageBrowserViewModel.swift 625–634, 891–901。

対策: metadataTaskを所有し、選択変更でcancel/restart。URLまたはselection generation一致時だけcommitし、panelを閉じたら停止する。

STATE-03 / P1

favoritesが二重のsource of truth

通常のfavoritesと統合用aggregatedFavoritesをViewModelにもactorにも保持する。統合モードで更新してもflat辞書しか更新されず、表示は古いaggregated値を読む。汎用rebuildFilteredIndices()は常にflat辞書を読む。

ImageBrowserViewModel.swift 958–1014, 1061–1071。

対策: favoritesはfolder-relative identityをkeyにした1正規形へ統合し、UIには派生snapshotだけを公開する。同名ファイルが複数folderにあるケースを必須テストにする。

LOG-01 / P1

ログポリシー不在で、機微値を明示的にpublic化

privacy: .publicは100箇所、うちパス・filename・URL・prompt・errorに関わる候補は79箇所。full path、生成AI prompt先頭100文字、localized errorをpublic指定している。独自navigation fileにもfilename/errorを平文保存する。folder pickerだけはprintを使用。

MetadataExtractor.swift 169–236 / NavigationDiagnostics.swift 18–19, 73–95 / MainWindowView.swift 548–562。

対策: CLAUDE.mdにpublic/private基準、category、level、保持期間、禁止値を定義。publicは件数・時間・列挙値だけ、path/name/errorはprivateまたはhash、promptは記録禁止。独自file logはopt-in、redaction、削除導線を持たせる。

FS-01 / P1

security-scoped resourceを開始しても停止しない

startはAppStateとViewModelの2箇所にあるが、productionからstopを呼ぶ箇所は0。しかも各々が別RecentFoldersStore instanceを持つため、開始したownerと終了すべきownerが分かれる。entitlementsはsandbox=falseなのにbookmark entitlementを有効化しており、設計意図も曖昧。

RecentFoldersStore.swift 135–163 / AIview.entitlements 5–10。

対策: 非sandbox配布を維持するなら不要なbookmark/entitlementを削除。sandbox化するならsceneのfolder leaseとしてownerを一本化し、切替・close・deinitでstopする。

ERR-01 / P1

エラーを握り潰し、空フォルダではloadingが終わらない

  • favorite操作はUI側でtry?により保存失敗を無視する。
  • folder importerはcancelと実エラーを区別せず、既存errorをclearしてprintする。
  • disk cache writeもtry?で観測不能。read-only mediaは仕様上あり得るため、dedupeしたdebug/warningが必要。
  • 空folderではfirst image callbackがないためisLoading=trueのままcompleteし、UIは「画像がありません」よりspinnerを優先する。

対策: userCancel / recoverable / invariant failureを型で区別。空complete時はloading=false。favorite失敗はtoast/alert、cache失敗はrate-limited logとmetricsへ。

BUILD-01 / P1

Strict Concurrencyを設定しているがSwift 5 modeのため、Swift 6 errorを見逃す

projectはSWIFT_STRICT_CONCURRENCY=completeだがSWIFT_VERSION=5.0。Swift 6を強制すると4件でbuild失敗した。

  • ImageLoader.Stateがnon-Sendable
  • CacheManager.stateとThumbnailCacheManager.stateがSendable classのmutable stored property
  • static ISO8601DateFormatterがnon-Sendable shared mutable state

対策: lock保護stateをOSAllocatedUnfairLock<State>等へ包むかactor化し、uncheckedを使うなら不変条件を文書化・テストする。CIにSwift 6 buildを追加して段階移行する。

CI-01 / P1

release前のquality gateがなく、用意されたコマンドも陳腐化

GitHub Actionsはrelease/update-tapだけでPR/push CIがない。release workflowもtest/lint/analyzeを通さずarchiveする。現環境でtask lintはSwiftLintの廃止済み--pathで失敗し、task format:checkも引数順が不正で失敗した。

直接実行ではSwiftLint 0.63.2が117件（serious 25）、SwiftFormat 0.61.1が56/63 filesを指摘。ただしproject設定ファイルとSwift version指定がないため、数自体を品質判定に使うべきではない。

対策: .swiftlint.yml / .swiftformat / .swift-versionを合意して固定し、PRでDebug build・unit test・Swift 6 build・lint・format・shellcheckを実施。release jobは同じquality jobへ依存させる。

5. 「場当たり的修正」があるか — 構造診断

ある。 ただし個々の修正コメントやテストは丁寧で、問題は開発姿勢ではなく、変更を受け止める状態モデルが足りないことにある。

状態の組を手動同期

currentIndex、targetIndex、currentImage、loadedImageURL、isLoadingを別々に更新する。1経路でも更新順を誤るとSTATE-01が生じる。

boolean / optional command bus

reload、zoom、sibling、open URLをset→全View監視→誰かがclearする。これはqueueでもscene-directed actionでもなく、複数consumerを持つと意味が崩れる。

症状修正の履歴

規模のシグナル: ImageBrowserViewModel.swiftは1,670行、MainWindowView.swiftは568行。SwiftLint既定値でもfile/type lengthとcomplexityに抵触する。ViewModelはfolder session、scan、navigation、image loading、favorites/filter、metadata、slideshow、cache、diagnosticsを同時に所有する。

推奨する中心モデル

現在のcommit単位

複数property + callback + unstructured Task

各methodが必要なpropertyを個別に揃える

→

BrowserSessionState

具体的には、FolderSessionController（scan generation）、ImageNavigationController（selection transaction）、FavoritesController、MetadataControllerへ責務を分ける。分割自体が目的ではなく、「古いoperationは現sessionへcommitできない」「表示対象は必ず1つのSelection」というルールを型で守ることが目的である。

6. CLAUDE.md と実装原則

CLAUDE.mdは存在し、仕様書の入口、文書更新ポリシー、per-folder thumbnail cacheの設計思想を明確にしている。実装も.aiview/<original>.jpg、mtime検証、read-only時に中央cacheへfallbackしない、という原則には概ね従っている。

書かれていて機能している

  • canonical specの所在
  • 文書更新のtrigger
  • 英日READMEの対応
  • cacheをdataと同じ場所へ置く理由
  • read-only mediaの扱い

不足している原則 — これ自体が問題

  • app-global / scene / view stateの所有範囲
  • Task owner、cancel、generation、commit rule
  • logging privacy、level、category、retention
  • error分類とUI/ログへの伝播
  • Swift version / concurrency policy
  • 必須quality gateとtest policy
  • telemetry data、retention、abuse protection

現在のCLAUDE.mdは「キャッシュのADR」としては良いが、project-wide implementation principlesとしては狭い。今回のP0/P1を直す際に、上記原則を先に追記し、修正コードをその原則の最初の適用例にするのがよい。

8. 推奨修正計画

安全確保（小さく先行）

LRUのweak linkとrelease test、empty folderのloading解除、privacy ON時の遅延Task cancel、prompt/path logging停止、stats credentialのheader移行とping rate limitを先に入れる。

Folder/Selection transaction導入

FolderSessionIDとSelectionを導入。Scannerをevent stream/resultにし、全await後commitをgeneration guard。metadata・warmer・prefetchをsession子Taskとして束ねる。

完了条件: A→B高速切替、列挙順≠sort順、subdirectory切替、cancel stormの回帰テスト。

scene state分離

AppStateをglobal services/settingsとwindow sessionへ分離し、メニューはfocused sceneへ配送。metricsとsecurity scopeもscene ownerに合わせる。

完了条件: 2windowで別folderを開き、zoom/reload/delete/pickerがfocused windowだけへ作用。

quality gate固定

CLAUDE.mdへ原則を追記し、SwiftLint/SwiftFormat設定とversionをcommit。PR CI、Swift 6 build、unit tests、analyze、ShellCheckをreleaseの前提にする。

完了条件: local TaskfileとCIが同じcommandを使用し、tag releaseがquality jobなしで進めない。

実測と文書同期

Instruments / TSanでwindow open-close、cache clear、slideshow、folder連打を測る。README cache treeとtelemetry disclosureを修正し、retention/deletion policyを公開する。

9. 良い点

設計・実装

  • App / Domain / Data / Presentationの4層は文書化され、依存注入できる主要serviceも多い。
  • @MainActor @ObservableをUI modelへ適用し、actor/lockを使う意識がある。
  • ThumbnailGeneratorのcontinuation resume guardとcancellation handlerは丁寧。
  • favorites/cacheのatomic write、legacy形式の後方互換がある。

検証・運用

  • テストコードが約7千行あり、favorites、cache、navigation、performanceまで広い。
  • shell scriptsはset -euo pipefailと入力path検証を使い、ShellCheckも通る。
  • WorkerはD1 prepared statements/bindとlast_seen indexを使用し、secret値自体はrepositoryへcommitしていない。
  • production sourceにfatalError、try!、明白なforce unwrapは見つからなかった。
